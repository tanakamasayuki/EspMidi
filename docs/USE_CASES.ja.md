# ユースケース

設計を検証するために使った具体的なシナリオです。各ユースケースが確定させた規則も記録します。仕様の正本は [DATA_MODEL.ja.md](DATA_MODEL.ja.md) / [ROUTING.ja.md](ROUTING.ja.md) です。

## UC1: 演奏を PC と外部音源へ同時に流す

USB MIDI キーボードの演奏を、USB Device 経由で PC へ渡しつつ、UART の外部音源へも同時に送る。

```text
USB Host 入力 ─┬─ USB Device 出力(PC)
               └─ UART 出力(外部音源)
```

**確定した規則。**

- 一対多は「同じ入力から複数のルート」で表現する。専用の分岐 API は持たない。
- **同一エンドポイントの入力から入ったメッセージは、既定では同じエンドポイントの出力へ送らない。** この構成で USB Host のキーボードへノートが返ると、機器によっては音が二重に鳴るか誤動作する。

## UC2: 複数機器を 1 台に集約し、PC から複数ポートに見せる

USB Host に MIDI キーボードと MIDI パッドをつなぎ、PC からは「Port 1: Keyboard」「Port 2: Pad」という 2 ポートの MIDI インターフェースとして見せる。

**確定した規則。**

- ポートは Endpoint > Port の 2 階層とし、**1 エンドポイントあたり最大 16 ポート**。USB MIDI 1.0 の cable と MIDI 2.0 の group がともに 4 bit なのに合わせる。
- USB Device 側が複数 cable を公開できる必要がある。現状の `EspUsbDevice` は 1 cable 固定なので[変更依頼](LIBRARY_REQUESTS.ja.md)を出した。
- USB Host 側は**接続時点でポート数が確定していなければならない**。トラフィックが届いた cable 番号から後追いで知る方式だと、無音のポートが存在しないことになり、出力方向のポート数は原理的に分からない。これも変更依頼になった。

## UC3: 音色ダンプ(長い SysEx)を転送する

USB Host につないだシンセから 10KB の音色ダンプを受け、UART の別のシンセへ流す。

**確定した規則。**

- **内部表現に UMP を採らない。** UMP の SysEx7 は 1 パケット 6 バイト固定で、10KB が約 1700 パケットになる。ポインタ + 長さのチャンクなら数百バイトを 1 メッセージで渡せる。
- **経路は開始時に確定する。** `chunkStart` で経路とフィルタ判定を決め、`chunkEnd` まで維持する。途中で判定が変わると壊れたストリームが出る。
- **出力ポートの SysEx は排他。** 転送中に別の入力の SysEx が同じ出力へ流れるとインターリーブして壊れる。

## UC4: 演奏中に機器を抜き差しする

ルーティングを組んだ後に USB MIDI 機器を抜き、別のポートに差し直す。

**確定した規則。**

- **ポートのハンドルは論理的な席で、切断しても失われない。** ルーティング設定は保持される。切断でハンドルが無効化されると、抜き差ししただけで全設定を組み直すことになる。
- **再接続時は識別子(VID / PID / serial)で照合して同じ席へ戻す。** USB のアドレスは差し直しで変わるので、アドレスを席の同一性に使えない。
- 切断中の出力ポートへの送信は失敗を返すが、致命的にはしない。機器の抜き差しは通常運用である。
- **進行中の SysEx は破棄するが、送り始めていた出力へは `0xF7` を送って閉じる。** 受け手を待たせ続けないため。

## UC5: BLE MIDI キーボードを UART 音源へ中継する

BLE MIDI キーボードを、BLE 非対応の音源へ UART で中継する。

**確定した規則。**

- BLE MIDI はタイムスタンプ(13 bit ミリ秒)を持ち、UART は持たない。**タイムスタンプは単位を型に持つ不透明値として運び、単位が違うポートへ転送するときは `None` に落とす。**
- `EspMidi` はタイムスタンプを解釈しない。値を読んで並べ替えたり遅延を補正したりはしない。異なる方式間の厳密な時刻同期は要件外。

## UC6: MIDI と HID を 1 台で兼ねる

USB Device で MIDI と HID を同時に公開し、ノート入力とキーボード入力を 1 台で担う。

**確定した規則。**

- **通信スタックはスケッチが所有する。** ポートは参照を受けて購読するだけで `begin()` を持たない。`EspMidi` がスタックを起動する設計だと、MIDI 以外のクラスと共存できない。
- `EspMidi` を使ったことで USB / BLE の基盤オブジェクトが隠蔽されてはならない。スケッチと他の処理が直接アクセスできる。
- **各基盤ライブラリの MIDI 便利 API は残す。** 片方向だけ使う構成で `EspMidi` を要求しない。

## UC7: 特定チャンネルだけ別の音源へ振り分ける

USB Host から来る ch1 を音源 A へ、ch10(ドラム)を音源 B へ振り分け、A へ送る分だけトランスポーズする。

**確定した規則。**

- **パイプラインは 3 段(入力ポート前処理 → ルート → 出力ポート後処理)。** ルート単位だけだと「この機器は ch1 と ch10 だけ使う」を全ルートに書く羽目になり、ポート群への共通後処理も書けない。
- 同じ入力に複数ルートがあるときは**ルートの登録順**に処理し、ルート間は独立とする。あるルートの変換が他のルートの入力を汚さない。

## UC8: SysEx 転送中も MIDI Clock を止めない

音色ダンプの転送中に、同じ出力へ MIDI Clock を送り続ける。

**確定した規則。**

- 出力ポートの SysEx 排他に例外を設ける。**System Real-Time(0xF8〜0xFF)だけは MIDI 仕様どおり割り込みを許す。** それ以外は待たせる。
- 待ちが長引いてバッファがあふれたら捨ててカウントする。カウンタは診断で読める。

## UC9: 双方向に接続して循環を作ってしまう

`A入力 → B出力` と `B入力 → A出力` を両方設定する。

**確定した規則。**

- **ルート追加時に到達可能性を検査し、循環を作るルートは拒否する。** 実行時にメッセージへ通過履歴を持たせる方式より、実行時コストがゼロで、エラーが演奏中ではなく設定時に分かる。
- ポートの席は動的に増えるが、ルートの端点は席なので検査は静的にできる。

## UC10: GPIO のつまみを既存の MIDI 経路に合流させる

ロータリーエンコーダを Control Change に変換し、USB Host から来る演奏と一緒に音源へ送る。

**確定した規則。**

- Control Mapping ヘルパーは**通信インターフェースではなくコントロール機能**として扱う。ただし生成されたメッセージは通常の入力ポートとして統合に参加する。
- ヘルパーは統合コアの必須部分ではない。使わない構成では include しないだけで済むよう分離する。
- GPIO の初期化・デバウンス・I/O エキスパンダ管理を `EspMidi` が必ず所有する設計にはしない。エンコーダの取りこぼしを防ぐサンプリング精度はヘルパー側の責任。

## UC11: 流れているものを見る

USB Host から来るノートをシリアルに表示し、受信したノートで LED を光らせる。設定用のディスプレイに現在のチャンネルを出す。

**確定した規則。**

- モニタは**アプリケーションポートへのルート 1 本**で表現する。専用の「モニタ機能」は作らない。
- アプリケーションポートは席・群・ループ規則を含めて他のポートと完全に同じ扱いにする。**アプリケーションは特別扱いではなくポートの 1 つ**。
- 「すべての入力 → アプリケーションポート」と書けば、後から挿した機器も自動的に監視対象になる(予約ハンドルの群)。

## UC12: 中身を見てアプリが処理する

ベロシティをテーブルで曲げる。CC の値が閾値を超えたら Program Change を送る。受信したノートからコード(和音)を作って送る。

**確定した規則。**

- **1 → 1 の書き換えと破棄は段のコールバック**で行う。ルート、入力ポート、出力ポートのどの段にも置ける。
- **1 → N、あるいは別種のメッセージを出す場合はアプリケーションポートへ書く。** コールバックは受け取ったメッセージを加工するだけで、新しいメッセージを産む口を持たない。
- **チャンク(SysEx)はコールバックを通らない。** データストリームの中身の解釈は EspMidi の役目ではなく、途中で経路判定を変えると SysEx 規則 1 と衝突する。SysEx を加工したいならアプリケーションポートで受けて自前で処理する。
- **コールバックからの `send()` は即時再帰しない。** キュー経由で次の `update()` に回るので、走行中のパイプラインに割り込まない。

## 原理的に扱えないこと(スコープ外として明記)

1. 異なる通信方式間の厳密な時刻同期と高精度スケジューリング。
2. 送信元が持っていないタイミング情報の復元。
3. MIDI メッセージの意味的な解釈を要する処理(和音の認識、演奏解析)。
4. 受信側の機器が SysEx をどう解釈するか。`EspMidi` は SysEx の中身を解釈しない。
5. 1 つの出力ポートに対する複数 SysEx ストリームの同時転送(MIDI プロトコル上不可能)。
