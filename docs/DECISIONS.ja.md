# 設計決定の台帳

基本方針として確定した決定と、その理由、採らなかった案を残します。正式な仕様は [DATA_MODEL.ja.md](DATA_MODEL.ja.md) / [ROUTING.ja.md](ROUTING.ja.md) / [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) に反映済みで、この文書は「なぜそうしたか」を記録します。

## 設計原則(確定)

[ESP32KeyBridge](https://github.com/tanakamasayuki/ESP32KeyBridge) の原則を MIDI へ翻訳したものです。

1. **EspMidi は MIDI を解釈しない。** ルーティング・フィルタ・変換に必要な最小限(status / channel / data1)だけを見る。SysEx の中身は解釈せず運ぶ。
2. **時間を持たない。** タイムスタンプは運ぶが解釈しない。時間依存処理はポート側。
3. **core は移植可能な純粋 C++。** プラットフォーム依存はポート層に閉じる。
4. **通信スタックはスケッチが所有する。** ポートは参照を受けて購読するだけで、スタックを起動しない。
5. **番号を受けて範囲チェックする公開 API を作らない。** 割り当ては自動採番(ハンドルを返す)。

## 決定 1: 中間表現は MIDI 1.0 バイト列。UMP は採らない

内部の正準表現を MIDI 1.0 のバイト列とし、UMP(Universal MIDI Packet)を内部表現にはしません。

**理由。** UMP の SysEx7 は 1 パケット 6 バイト固定です。10KB の音色ダンプが約 1700 パケットになり、USB → UART の素通し転送でも 6 バイトごとに詰め替えが発生します。「長い SysEx を扱える」は要件なので、これは実装の都合ではなく要件との衝突です。ポインタ + 長さのチャンクなら数百バイトを 1 メッセージで渡せます。

加えて、MIDI 2.0 対応の本当の重さは UMP の器ではなく MIDI-CI(プロトコル交渉・プロファイル・プロパティ交換)側にあり、器だけ先取りしても得が小さいのに初期の複雑度は上がります。「将来の可能性のために初期設計を過度に複雑化しない」に反します。

**代わりに、MIDI 2.0 で行き止まりになる箇所だけを先に外しました。**

| 行き止まり | 対処 |
| --- | --- |
| チャンネルが 16 で頭打ち | `PortId` が cable / group を吸収し、座標を `(PortId, channel)` の 256 空間にする |
| 器が 3 バイトに固定される | `status` / `data1` / `data2` に加えて `raw` + `length` を併せ持つ |
| メッセージ種別の番号が振り直しになる | `MessageType` を UMP の Message Type と同一の番号体系で採番する |
| タイムスタンプの単位が固定される | 単位を型に持つ不透明値にする(BLE の 13 bit ms と JR Timestamp の両方が入る) |
| チャンクが SysEx 専用概念になる | `chunk` / `chunkStart` / `chunkEnd` として一般化する(SysEx7 / SysEx8 / Flex Data 共通) |
| 変換 API が 7 bit 固定になる | 変換 API に「7 bit」と名乗らせない。幅の広い版を後から非破壊で足せる形にする |

**却下した案: UMP を内部表現にする。** 上記のとおり長い SysEx の要件と衝突し、初期複雑度も上がるため。将来 MIDI 2.0 へ対応するときは `MessageType` に 0x4 / 0x5 を足し、64 / 128 bit のアクセサを足し、MIDI 1.0 ⇔ 2.0 のスケーリングをポートの縁に置く。ルーティング・フィルタ・ポート管理は触らない。

## 決定 2: 依存は EspMidi → transport の一方向。transport 側の MIDI 層は残す

`EspMidi` は各基盤ライブラリに依存しますが、基盤ライブラリが `EspMidi` に依存することはありません。そして**各基盤ライブラリの MIDI 便利ラッパーと example は残します**。

**理由。** `EspMidi` は任意のライブラリです。MIDI 入力だけ、あるいは出力だけを片方向に使う構成なら基盤ライブラリを直接使えば済み、そのために `EspMidi` を要求してはいけません。`EspMidi` に価値が出るのは複数のインターフェースが出会う場所だけです。

この結果、**破壊的変更は原則不要**になりました。`EspMidi` は既存の層を消さずに横に乗るだけなので、変更依頼が必要なのは RAW 層の能力が足りない箇所だけです([LIBRARY_REQUESTS.ja.md](LIBRARY_REQUESTS.ja.md) に 2 件、いずれも非破壊の追加)。

### ポートごとに transport のどの層に乗るか

原則は「transport 側にワイヤ形式の実装があり、既にテストされているならそれに乗る。無い場合だけ `EspMidi` が持つ」です。

| ポート | 乗る層 | 理由 |
| --- | --- | --- |
| UART | `HardwareSerial` の生バイト | 実装が存在しない |
| USB Device | `readPacket` / `writePacket` の生パケット | 便利層が薄い(SysEx なし・cable 1 本) |
| USB Host | `EspUsbHostMidiMessage` + `midiSend` の生バイト | CIN 分解はあるが SysEx 連結が無いので完全版は `EspMidi` が持つ |
| BLE | `EspBleMidiDevice` / `EspBleMidiHost` | 下記 |

**BLE で生 GATT に降りない理由。** 3 つあります。

1. BLE MIDI のタイムスタンプと SysEx 分割は最も繊細な部分で、2 実装持ちたくない。`EspBleMidi.h` 自身が「the tables and parsing rules are the specification, not house style」と書いており、`EspBle` 側には `tests/unit/midi/midi_test.cpp` というホスト側コーデックテストが既にある。
2. GATT サービスの二重登録が構造的に起きない。生 GATT に降りると、スケッチが `EspBle` の MIDI と `EspMidi` の BLE ポートを両方使ったときに同じ UUID のサービスを 2 つ登録する事故が起きえる。乗る形なら「スケッチが `EspBleMidiDevice` を 1 つ作って渡す」ので余地がない。
3. 設計原則 4(通信スタックはスケッチが所有し、ポートは参照を受けて購読するだけ)と一致する。

**却下した案 A(KeyBridge 踏襲・transport の MIDI をそのまま残し `EspMidi` も独自コーデックを持つ)。** MIDI 1.0 バイトストリームの解析が `EspMidi` と `EspBle` に重複する。決定 2 の形では BLE のワイヤ形式を `EspBle` に委ねるので重複しない。

**却下した案 B(依存反転。`EspMidi` は core のみ、ポート実装は各 transport 側)。** 移行コストは小さいが、ポートの抽象が 4 リポジトリに跨る公開契約になり、`EspMidi` 側で抽象を変えるたびに 4 リポジトリが追随する。MIDI 2.0 対応も 4 リポジトリ同時進行になる。

**却下した案 C(MIDI 集約。transport から MIDI を撤去し `EspMidi` が全部持つ)。** 当初これを推していたが 2 つの根拠が消えた。(1) `EspMidi` が必須になり「片方向なら不要」という位置づけと両立しない。(2) 最大の論拠だった `EspBle` / `EspBleBluedroid` 間のコーデック複製は、`EspBleBluedroid` を `EspBle` へ統合する方針により別ルートで解決する。加えて移行コストが大きい(example 9 本、テストスイート 9 個、docs 4 リポジトリ)。

## 決定 3: ポートは Endpoint > Port の 2 階層。ハンドルは論理的な席

**1 エンドポイントあたり最大 16 ポート。** USB MIDI 1.0 の cable が 4 bit、UMP の group が 4 bit で一致するためこの上限を選びました。MIDI 2.0 に移ってもポート数の上限が変わりません。

**入力ポートと出力ポートは別の実体だが、所属エンドポイントは判別できる。** MIDI の物理も IN / OUT が独立しているためで、副産物としてループ防止の既定(同一エンドポイントへ戻さない)が構造的に成立します。

**ハンドルは論理的な席で、切断しても失われない。** 切断でハンドルが無効化されるとルーティング設定が全部壊れ、機器を抜き差ししただけでアプリケーションが再設定を強いられます。席モデルなら「動作中に構成を変更できる」「切断に追従できる」「無効になったポートを安全に扱える」が同時に満たせます。

**再接続時は識別子(VID / PID / serial、BLE アドレス)で照合し、同じ席へ戻す。** 識別できない機器は新しい席にします。

**却下した案: 切断のたびに新しい席を割り当てる。** 実装は単純だが、機器を抜き差ししただけでルーティングが切れる。

**ポート群への動的ポートの参加は明示追加のみ。** 「条件に一致するポートは自動参加」は便利だが、動的ポートの出入りと群の定義の相互作用が複雑になるため初期には入れません。「すべての入力」「すべての出力」は暗黙の群として持ちます。

## 決定 4: ルートは第一級。3 段パイプライン、キュー駆動、SysEx 3 規則

**ルートを第一級オブジェクトにする。** 一対一 / 一対多 / 多対一 / 多対多がすべてルートの組み合わせで出て、ルートごとにフィルタと変換を持てます。

**パイプラインは 3 段(入力ポート前処理 → ルート → 出力ポート後処理)。** ルート単位だけに限ると「この機器は ch1 だけ」を全ルートに書く羽目になり、ポート群への共通の後処理も書けません。同じ入力の複数ルートはルートの登録順に処理し、ルート間は独立とします。

**駆動はキュー + コピー + 明示 `update()`。** 受信コールバックは USB Host タスクや NimBLE ホストタスクの文脈で走るので、そこから別の transport へ直接送信しません。MIDI 1.0 のメッセージは最大 3 バイトなのでキューのコピーコストは無視でき、SysEx はチャンク単位でコピーします。あふれたら捨ててカウントします。

**却下した案: 同期パススルー(受信コールバック内でルーティングから送信まで完了)。** ゼロコピーで最低遅延だが、transport のタスク文脈から別の transport へ送信することになり、設計原則(時間・割り込み・タスクはポート内部に閉じる)にも反する。

**SysEx の 3 規則。**

1. **経路は開始時に確定する。** `chunkStart` で経路とフィルタ判定を決め、`chunkEnd` まで維持する。途中でルーティングが変更されても進行中のストリームは守る。ESP32KeyBridge の「レイヤーの置換は press 時に確定し release は確定値を離す(stuck 防止)」と同じ思想。
2. **切断時はストリームを閉じる。** 未完 SysEx は破棄するが、送り始めていた出力へは `0xF7` を送る。受け手を待たせ続けないため。ESP32KeyBridge の「入力の切断時は押下集合をクリアして全 release」と同型。壊れた SysEx を渡すより何も渡さないほうがよいという考え方もありえるが、閉じないと受け手が待ち続けるほうが害が大きいと判断した。
3. **出力ポートの SysEx は排他。** ただし System Real-Time(0xF8〜0xFF)だけは MIDI 仕様どおり割り込みを許す(SysEx 転送中に MIDI Clock が止まらないため)。**ストリーム送信中に送れない通常メッセージは、当初「待たせる」としていたが「捨ててカウント」へ変更した**(Phase 3 の実装時)。待たせるには出力ごとの遅延バッファが必要で、容量管理と順序保証という別の問題を持ち込む。MIDI のワイヤ上でも `0xF0` と `0xF7` の間に通常メッセージは送れないので、遅れて届くより落ちたと分かるほうが診断できる。

いずれも MIDI 2.0 で変わりません。UMP でもデータメッセージのストリームは group ごとに同時 1 本という制約です。

**ループ防止は同一エンドポイント既定禁止のみ。** ルート単位で解除できます。

**当初あった「多段の循環の静的検査」は削除しました**(Phase 3 の設計時)。ルーティングは In → Out の一方向で内部に Out → In の辺が無いため、**内部で循環が起きません**。`A入力 → B出力` と `B入力 → A出力` を両方設定しても、A の演奏は B へ出てそこで終わります。戻るとしたら機器 B のエコーバックで、それは EspMidi から見えない外部配線です。検査対象が存在しないコードになるため落としました。実在する循環(同一エンドポイントへの送り返し、アプリケーションポートの自己ループ)はどちらも既定規則が覆います。

## 決定 5: unit は g++ 直接方式。loopback カテゴリを持つ

**`unit/` は subject ごとのディレクトリで g++ を直接呼ぶ。** core が純粋 C++ なのでこれが素直に効き、`-Wall -Wextra -Werror` でヘッダを直接検査でき、arduino-cli 不要で CI が数秒で終わります。`EspBle` の `tests/unit/` と同じ流儀です。

**Arduino ライブラリとしての include / build 経路は `arduino_smoke/` で担保する。** ESP32KeyBridge が host profile を使う理由(環境の g++ を直接呼ぶだけでは Arduino ライブラリとしての経路が検証されない)は正当なので、小さな別カテゴリとして持ちます。同じスケッチを `--profile esp32s3` で実機でも走らせます。

**却下した案: ESP32KeyBridge 流の単一 `.ino` を host profile でビルドする方式に統一する。** subject が多い(codec / port model / routing / filter / transform / SysEx 規則)ので 1 ファイルが肥大化し、CI も遅くなる。ESP32KeyBridge の `core_smoke.ino` は 76KB に達している。

**`loopback/` カテゴリを持つ。** `EspMidi` は複数ポートを 1 つのシステムとして扱うライブラリなので、1 台で全ポートを同時に動かす構成が最も本質に近いためです。`EspUsbDevice` の `tests/loopback/` に先例があります。

**UART は配線ゼロのループバックを第一のテストにする。** GPIO マトリクスで UART1_TX と UART2_RX を同一 GPIO に割り当てれば、実ペリフェラル 2 つを通しつつ配線が不要です。peer 2 台のテストも既存の USB peer 配線(GPIO19↔19 / GPIO20↔20、ストレート)のまま、役割ごとに TX / RX の割り当てを逆にすればクロス結線として使えます。実 MIDI DIN(フォトカプラ・220Ω・5V カレントループ)の検証だけが実配線を要するので `manual/` に隔離します。

**全プロファイルに兄弟ライブラリの released 版と local 版を並べる。** `EspMidi` は 3 ライブラリに依存し、そのうち 2 つには変更依頼を出しているため、開発版と同時に進める手段が必要です。`EspUsbDevice` の `p4_loopback` / `p4_loopback_local` と同じ形にします。

## 決定 6: アプリケーションはポートとしてパイプラインに参加する

「EspMidi は MIDI を解釈しない」という原則は EspMidi 自身の話であって、**アプリケーションが中身を見て処理したい需要**は別に存在します。当初の仕様にはその方法がなく、しかも UC10 で「Control Mapping ヘルパーが生成したメッセージは通常の入力ポートとして統合に参加する」と約束済みでした。

**2 つの仕組みを入れます。**

**アプリケーションポート(主役)。** トランスポートに裏打ちされないポートで、スケッチが注入し、受け取ります。席・群・ループ規則・ルーティングは他のポートと完全に同じで、**アプリケーションは特別扱いではなくポートの 1 つ**になります。ESP32KeyBridge の `ManualInput` と Serial 出力アダプタの前例と同型で、設計原則 4 とも一致します。モニタも Control Mapping ヘルパーもこの上に乗ります。

**段のコールバック(補助)。** 3 段パイプラインのどの段にもユーザーコードを置け、その場で書き換えるか `Drop` で落とせます。

**なぜ両方か。** コールバックだけでは「アプリが能動的にメッセージを作る」(Control Mapping、クロック生成)が書けません。アプリケーションポートだけでは、ベロシティを曲げるだけでルートが 2 本に割れて経路が読みにくくなり、ループ規則の判定も複雑になります。役割が違います。

**確定した制約。**

- コールバックは `update()` の中で走る。トランスポートのタスク文脈では走らない。
- **チャンクはコールバックを通さない。** データストリームの解釈は EspMidi の役目ではなく、途中で経路判定を変えることは SysEx 規則 1 と衝突する。加工したいならアプリケーションポートで受ける。
- **`send()` は即時再帰しない。** キューに積まれ次の `update()` で処理されるので、段やコールバックの中から呼んでも走行中のパイプラインに割り込まない。
- `update()` が処理するのは呼び出し時点で積まれていた分だけ。アプリのフィードバックが 1 回の `update()` を無限に回すことがない。

## 仮置き(実装で最終確定)

1. ~~フィルタと変換の具体的な API 形状~~ → **段は 3 種類の規則を持つ**(フィルタ → 変換 → コールバックの順)。フィルタは絞るだけ、変換は書き換えるだけ、コールバックは両方。**値の幅は `ValueMap` が端点を正規化して保持する**ことで将来広げられる形にした(`range7()` / `scale7()` / `fixed7()` は「7 bit 単位で書いた」ことを表すだけで、`ValueMap` 自体は幅を持たない)。ノート番号・チャンネル・CC 番号は MIDI 2.0 でも同じ幅なのでただの整数のまま。**変換に付け替え表は持たない** — 「CC7 を CC11 へ」はフィルタで絞って変換で番号を設定する組み合わせで書け、複数の付け替えは複数のルートになる。Phase 4 で確定。
2. ~~キューの深さと SysEx 一時バッファのサイズの既定値~~ → `ESPMIDI_QUEUE_ENTRIES` 32 / `ESPMIDI_CHUNK_BYTES` 48(1 エントリ約 64 バイト、合計約 2KB)。エントリを超えるチャンクは分割する。Phase 3 で確定。
3. ~~ポート群の暗黙の群(すべての入力 / すべての出力)をハンドルとして露出するか~~ → **予約ハンドルとして露出する**(`InGroup::all()` / `OutGroup::all()`)。ルートの端点が「ポートまたはポート群」で統一され、後から挿した機器が更新なしで群に含まれる。Phase 2 で確定。

## 将来メモ(初期スコープ外)

- **MIDI 2.0 / UMP。** 決定 1 の表のとおり、器の側は地続きにしてある。`EspUsbDevice` が同梱する TinyUSB には USB-MIDI 2.0 の descriptor テンプレート(`TUD_MIDI2_DESC_ALT1_HEAD` / Group Terminal Block)が既に入っているので、USB Device 側は実装経路が用意されている状態。MIDI-CI(プロトコル交渉・プロファイル・プロパティ交換)は別途大きい。
- **AppleMIDI / RTP-MIDI。** ネットワーク、セッション、同期、探索、再接続の責務が大きく、ポート統合とは別。将来、外部拡張としてポートへ接続できる設計は維持する。
- **タイムスタンプを解釈する遅延補正・スケジューリング。** 設計原則 2 を破るので、実需要が出たらポート側の機能として検討する。
- **異なる方式間の厳密な時刻同期。**
- **cable / jack 名の PC 側への公開。** [LIBRARY_REQUESTS.ja.md](LIBRARY_REQUESTS.ja.md) の依頼 1・2 の後半部分。ポート数対応より優先度が低い。
