# 要件

`EspMidi` は、ESP32 シリーズ上の複数の MIDI 入出力を共通のポートとして統合し、その間でメッセージを転送・複製・統合・振り分けするための Arduino 向けライブラリです。

## 目的

本ライブラリは MIDI の通信方式そのものを実装しません。`EspUsbHost` / `EspUsbDevice` / `EspBle` が提供する MIDI 機能と、本リポジトリ同梱の UART MIDI を、接続方式ではなく**論理的な MIDI ポート**として扱い、その上に統合層を提供します。

```text
入力インターフェース
        ↓
共通 MIDI 表現
        ↓
統合・変換・振り分け
        ↓
出力インターフェース
```

満たすべき目的は次のとおりです。

- 異なる MIDI インターフェースを共通の概念で扱う
- 単独のポートだけでも利用できる(統合が必須要件にならない)
- ポート間でメッセージを転送する(一対一 / 一対多 / 多対一 / 多対多)
- 複数のポートを論理的な入力群・出力群としてまとめる
- 条件に応じた振り分け、フィルタリング、基本的な変換を行う
- USB / BLE の MIDI 以外の機能と共存する
- 各インターフェースの初期化とライフサイクルをアプリケーション側に残す
- 診断に必要な情報を統合によって失わない

## 位置付け

**`EspMidi` は任意です。** MIDI 入力だけ、あるいは MIDI 出力だけを片方向に使う構成なら、`EspUsbHost` / `EspUsbDevice` / `EspBle` を直接使えば済みます。各ライブラリはそのための MIDI 便利 API と example を持ち続けます。

`EspMidi` に価値が出るのは、**複数のインターフェースが出会う場所**です。USB Host で受けた演奏を USB Device と BLE と UART へ同時に流す、複数の入力を 1 つの音源へ統合する、経路ごとにチャンネルを差し替える、といった構成が対象です。

依存の向きは `EspMidi` → 各基盤ライブラリの一方向だけです。基盤ライブラリが `EspMidi` に依存することはありません。

## 対応プラットフォーム

- Arduino フレームワーク
- Arduino-ESP32
- ESP32 シリーズ

汎用 C++ ライブラリ化や ESP32 以外の Arduino ボードへの移植は主要目的としません。ただし MIDI メッセージ処理とルーティングは ESP32 固有 API に依存させず、ホスト上でテストできる純粋 C++ とします([CORE_DESIGN.ja.md](CORE_DESIGN.ja.md))。

実際に使えるインターフェースは SoC と基盤ライブラリの対応範囲で決まります。USB Host / USB Device は USB OTG を持つ ESP32-S2 / ESP32-S3 / ESP32-P4 が主な対象です。BLE は SoC と Arduino-ESP32 の Bluetooth バックエンドに応じて `EspBle` を使います。すべての ESP32 で全インターフェースが使えることは保証しません。

## ライブラリの役割

`EspMidi` は USB Host、USB Device、BLE の通信基盤を初期化・停止・破棄しません。基盤の所有権はアプリケーションと各基盤ライブラリに残します。

```text
アプリケーション
├─ EspUsbHost      MIDI / HID / CDC / MSC / Audio / ...
├─ EspUsbDevice    MIDI / HID / CDC / ...
├─ EspBle          MIDI / HID / 独自 GATT / Central / Peripheral
└─ EspMidi
   ├─ MIDI ポートの統合
   ├─ MIDI ルーティング
   ├─ MIDI フィルタ
   ├─ MIDI 変換
   └─ 複数ポート管理
```

`EspMidi` は次を行いません。

- USB Host / USB Device / BLE スタックの起動と停止
- BLE Advertising の管理
- 外部で生成されたオブジェクトの破棄
- MIDI 以外の USB クラスや BLE サービスの管理

`EspMidi` を使ったことで USB や BLE の基盤オブジェクトが隠蔽されてはなりません。

## 共通 MIDI 表現

異なるインターフェースから受信したメッセージを、内部では共通の意味として扱います。通信方式固有のパケット形式はポート側で処理し、統合処理では Note、Control Change、Program Change などの MIDI 上の意味を中心に扱います。

内部正準表現は MIDI 1.0 のバイト列とします。ただしメッセージ種別の番号体系・チャンネル座標・タイムスタンプの持ち方を MIDI 2.0(UMP)に地続きな形にします。詳細は [DATA_MODEL.ja.md](DATA_MODEL.ja.md)、判断の理由は [DECISIONS.ja.md](DECISIONS.ja.md) の決定 1 を参照してください。

要件は次のとおりです。

- 受信したメッセージがどのポートから来たかを識別できる
- 複数入力を統合した後も送信元を参照できる
- MIDI 1.0 の全メッセージを対象とする(Note On / Note Off / Polyphonic Key Pressure / Control Change / Program Change / Channel Pressure / Pitch Bend / System Common / System Real-Time / System Exclusive)
- **System Exclusive は短いメッセージだけを前提にしない。** USB / BLE / UART でサイズと分割方法が異なることを踏まえ、長い SysEx を扱える
- 通信方式側がタイミング情報を持つ場合(BLE MIDI のタイムスタンプなど)、その情報を失わない。ただし異なる方式間の厳密な時刻同期や高精度スケジューリングは初期必須要件としない

## ポートモデル

中心概念は通信方式ではなく論理的な MIDI ポートです。階層は 2 段とし、1 エンドポイントあたり最大 16 ポートとします(USB MIDI 1.0 の cable と MIDI 2.0 の group がともに 4 bit であることに合わせています)。

```text
Endpoint(接続の単位。切断はここで起きる)
 └─ Port(ルーティングの座標)
     ├─ In  Port
     └─ Out Port
```

- 入力ポートと出力ポートは別の実体とし、所属エンドポイントは判別できる
- ポートのハンドルは論理的な席として扱い、切断しても失われずルーティング設定を保持する
- 同じ機器が再接続したら識別子の照合で同じ席へ戻る
- 複数のポートを用途別の群としてまとめられる(すべての出力 / 外部音源 / 制御用 / クロック用 など)

詳細は [DATA_MODEL.ja.md](DATA_MODEL.ja.md) を参照してください。

## 対象 MIDI インターフェース

初期の標準対象は次の 5 つです。各ポートの実装状況は [PORTS.ja.md](PORTS.ja.md) を参照してください。

| ポート | 基盤 | 備考 |
| --- | --- | --- |
| USB Device MIDI | `EspUsbDevice` | MIDI 単独構成と、HID / CDC / MSC を含む複合 USB Device の双方で使える |
| USB Host MIDI | `EspUsbHost` | 動的な接続・切断、複数機器、USB ハブ経由、MIDI 以外の機器との共存、複合機器、1 接続が複数論理ポートを持つ場合 |
| BLE MIDI Device | `EspBle` | ESP32 が BLE MIDI 機器として振る舞う |
| BLE MIDI Host | `EspBle` | ESP32 が外部の BLE MIDI 機器へ接続する |
| UART MIDI | 本リポジトリ同梱 | MIDI プロトコルと物理 UART の結び付きが強いため標準機能として同梱するが、統合コアとは分離する |

BLE MIDI は他の GATT サービスや BLE HID と共存できること、USB MIDI は他の USB クラスと共存できることを要件とします。`EspMidi` は BLE スタック、接続、セキュリティ、Advertising などの一般的な BLE 管理を担当しません。

## ルーティング

入力元と出力先の対応関係を、通信方式ではなく論理ポート間の関係として管理します。

- 入力元を識別でき、出力先を指定できる
- 1 つの入力に複数の出力を割り当てられる
- 複数の入力を同じ出力へ割り当てられる
- 動作中に構成を変更できる
- 接続・切断に追従でき、無効になったポートを安全に扱える
- **意図しない循環転送を防止できる**

ルーティング処理は各基盤ライブラリの内部へ分散させず、`EspMidi` 側で統一的に扱います。詳細は [ROUTING.ja.md](ROUTING.ja.md) を参照してください。

## フィルタリングと変換

単純転送だけでなく、基本的な条件指定と変換を行えることを要件とします。

**フィルタの条件**: メッセージ種別、MIDI チャンネル、ノート範囲、Control Change 番号、送信元ポート、その他の基本的な MIDI 属性。

**変換の対象**: MIDI チャンネルの変更、ノート番号の変更、トランスポーズ、Velocity 値の変更、Control Change 番号の変更、Control Change 値の範囲変換。

高度なシーケンサー、MIDI エフェクター、スクリプトエンジンの内蔵は目的としません。

## Control Mapping ヘルパー

GPIO、ADC、エンコーダなどは MIDI 通信インターフェースそのものではなく、外部入力を MIDI へ変換したり MIDI を外部出力へ反映したりする**コントロール機能**として扱います。

本リポジトリへ同梱してよいものとしますが、統合コアの必須部分ではなく、使わなくてもよい補助機能として明確に分離します。

対象例: ボタン → Note、ボタン → Control Change、アナログ入力 → Control Change、エンコーダ → Control Change、Note 受信による LED 制御、Control Change 受信による出力制御、外部クロックと MIDI Clock の変換。

入力元を ESP32 の GPIO 番号だけに固定せず、ADC、タッチ入力、I/O エキスパンダ、キーマトリクス、外部入力ライブラリを同じ考え方で使える余地を残します。GPIO 初期化、デバウンス、I/O エキスパンダ管理を `EspMidi` が必ず所有する設計にはしません。

## ライフサイクル

USB / BLE 基盤の初期化順序はアプリケーションが決めます。`EspMidi` は、すでに利用可能なインターフェースを登録できることを基本とします。

動的な接続を持つインターフェースについては、ポートの追加・削除、一時的な切断、再接続、接続先の変更、複数機器の識別を扱えることを要件とします。

`EspMidi` の開始と終了が、外部所有されている USB / BLE 基盤の開始と終了を暗黙に引き起こしてはなりません。

## エラーと状態の可視性

統合によって各インターフェースの状態が隠れすぎないことを要件とします。少なくとも次を確認できるようにします。

- ポートが利用可能か / 接続中か
- メッセージを送信できるか / 送信が失敗したか
- 入力が破棄されたか
- 出力が混雑しているか
- どのポートで問題が発生したか
- USB / BLE 機器が切断されたか

## 共存性

`EspMidi` を使ったことで次の構成が妨げられてはなりません。

- USB Device で MIDI と HID を同時に公開する
- USB Device で MIDI と CDC を同時に公開する
- USB Host で MIDI 機器とキーボードを同時に使う
- USB Host で MIDI を含む複合機器を使う
- BLE MIDI と BLE HID を同時に使う
- BLE MIDI と独自 GATT サービスを同時に使う
- USB Host、USB Device、BLE、UART を同時に使う
- `EspMidi` 以外の処理が各基盤ライブラリへ直接アクセスする

## 拡張性

将来新しい MIDI インターフェースを追加できることを要件とします。追加対象が本リポジトリ内に存在する必要はなく、外部ライブラリが共通ポートとして参加できる設計を目指します。

将来候補: MIDI 2.0 / Universal MIDI Packet、RTP-MIDI、独自ネットワーク MIDI、外部 UART 拡張、SPI / I2C 経由の MIDI ブリッジ、CV/Gate や DIN Sync との変換。

ただし将来の可能性のために初期設計を過度に複雑化しません。この方針のもとで MIDI 2.0 に対して何を先に決め、何を先送りしたかは [DECISIONS.ja.md](DECISIONS.ja.md) の決定 1 に記録しています。

## 非目標

初期段階では次を主要目的としません。

**AppleMIDI / RTP-MIDI**: ネットワーク、セッション、同期、探索、再接続など、ポート統合とは別の責務が大きいため初期の標準対象に含めません。将来、外部拡張としてポートへ接続できる設計は維持します。

**あらゆる MIDI 通信方式**: RTP-MIDI、Web MIDI、WebSocket MIDI、OSC、ESP-NOW MIDI、独自無線 MIDI を初期標準機能として要求しません。

**DAW / シーケンサー機能**: MIDI シーケンサー、楽曲編集、ピアノロール、SMF ファイルの総合編集、DAW 機能、ソフトウェアシンセサイザー、音声生成。

**USB / BLE 基盤の再実装**: `EspUsbHost` / `EspUsbDevice` / `EspBle` が担う汎用機能を `EspMidi` 内へ重複実装しません。

**MIDI 以外の通信データの統合**: USB HID、USB Audio、BLE HID、CDC、MSC などのデータは統合管理しません。ただしそれらが同じ基盤上で MIDI と共存することは重要な要件です。

## 想定利用例

- USB MIDI キーボードの演奏を、USB Device 経由で PC へ渡しつつ UART の外部音源へも同時に送る
- BLE MIDI キーボードを、BLE 非対応の音源へ UART / USB で中継する
- 複数の MIDI 機器を 1 台の ESP32 に集約し、PC からは複数ポートの MIDI インターフェースとして見せる
- 特定チャンネルだけを別の音源へ振り分ける
- 受信したノートをトランスポーズして別チャンネルへ送る
- MIDI と HID を同時に公開し、ノート入力とキーボード入力を 1 台で兼ねる
- GPIO のボタンとエンコーダを Control Change に変換し、既存の MIDI 経路へ合流させる

## ESP32KeyBridge との関係

[ESP32KeyBridge](https://github.com/tanakamasayuki/ESP32KeyBridge) と統合思想を共有します。入力を共通表現へ正規化し、変換を適用し、必要に応じて統合して 1 つ以上の出力へ送るという構造、ハードウェア固有処理をアダプタ側へ分離する方針、リポジトリ構成・ドキュメント構成・テスト方針は共通です。

一方、キーボードと MIDI では状態モデルが異なります。キーボードが「押下集合」という状態を中心に据えるのに対し、MIDI は本質的にイベント列です。ESP32KeyBridge の内部モデルをそのまま再利用することは目的としません。

## 非機能要件

- ハードウェア非依存部分(共通表現、ルーティング、フィルタ、変換)はホスト上でテストできる
- 実機を要するテストは、シリアルログだけで期待値を assert できる範囲に限定する
- 複合構成(MIDI + HID、MIDI + CDC、複数インターフェース同時)を主要なテスト対象にする
- 基盤ライブラリとの間で MIDI 用語と意味を統一し、同じ MIDI 機能に異なる挙動を持たせない
