# ルーティング

ポート間の転送、パイプライン、駆動モデル、SysEx の規則、ループ防止の仕様です。この文書は**仕様**を書きます。実装状況は [DEVELOPMENT_PLAN.ja.md](DEVELOPMENT_PLAN.ja.md) を、判断の理由は [DECISIONS.ja.md](DECISIONS.ja.md) を参照してください。

前提となるメッセージとポートの形は [DATA_MODEL.ja.md](DATA_MODEL.ja.md) にあります。

## ルートは第一級オブジェクト

入力元と出力先の対応関係を `Route` として持ちます。ハンドルは自動採番です。

```cpp
espmidi::Route r = midi.addRoute(inPort, outPort);
midi.addRoute(inPort, synths);   // 端点にポート群も指定できる
```

これで [REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) の 4 形態がすべて出ます。

| 形態 | 表現 |
| --- | --- |
| 一対一 | ルート 1 本 |
| 一対多 | 同じ入力から複数のルート |
| 多対一 | 複数のルートが同じ出力へ |
| 多対多 | 上記の組み合わせ |

「全入力から全出力へ」という固定構成ではなく、組み合わせを個別に管理できます。ルートは動作中に追加・削除できます。

## パイプラインは 3 段

```text
入力ポート前処理 ──→ ルート(フィルタ + 変換) ──→ 出力ポート後処理

「この機器は              「この経路だけ              「この出力は常に
 ch1 しか使わない」        トランスポーズ +2」          ch1 に固定」
```

3 段すべてにフィルタと変換を置けます。ルート単位だけに限ると「この機器は ch1 だけ」を全ルートへ書く羽目になり、ポート群への共通の後処理も書けません。

各段は**3 種類の規則**を持てます。適用順は常に次のとおりです。

```text
フィルタ(宣言的) → 変換(宣言的) → コールバック(ユーザーコード)
```

- **フィルタ**は絞るだけ。種別、チャンネル、ノート範囲、Control Change 番号で通過を決めます。
- **変換**は書き換えるだけ。チャンネル、トランスポーズ、Velocity、Control Change 番号と値、プレッシャー。
- **コールバック**は両方できます。その場で書き換えるか `Verdict::Drop` で落とします。

何も設定しなければ段は素通しです。

```cpp
espmidi::Filter onlyVolume;
onlyVolume.kinds = espmidi::KindControlChange;
onlyVolume.ccMin = onlyVolume.ccMax = 7;
router.setRouteFilter(route, onlyVolume);

espmidi::Transform toExpression;
toExpression.controller = 11;                              // CC7 → CC11
toExpression.velocity = espmidi::ValueMap::scale7(0, 63);  // 音量を半分に
router.setRouteTransform(route, toExpression);

router.setRouteCallback(route, myCode, this);              // 任意コード
```

**「CC7 を CC11 にする」は、CC7 に絞ったフィルタと番号を設定する変換の組み合わせ**です。変換側に対応表を持たないのはこのためで、複数の付け替えは複数のルートになります。

1 つのメッセージから別種のメッセージを出したい場合や、1 → N にしたい場合はコールバックからアプリケーションポートへ書きます(後述)。

### 値の解像度

Velocity と Control Change 値は MIDI 1.0 では 7 bit、MIDI 2.0 では 16 / 32 bit です。**`ValueMap` は端点を正規化して保持する**ので、いま書いた規則は幅が広がっても同じ意味を保ちます([DECISIONS.ja.md](DECISIONS.ja.md) の決定 1)。

```cpp
espmidi::ValueMap::scale7(0, 63);          // 入力全域を下半分へ(音量制限)
espmidi::ValueMap::range7(32, 96, 0, 127); // 32〜96 を全域へ(範囲外はクランプ)
espmidi::ValueMap::fixed7(100);            // 常に一定(タッチ非対応のパッド)
espmidi::ValueMap::range7(0, 127, 127, 0); // 反転(逆配線のペダル)
```

ノート番号、チャンネル、Control Change 番号は MIDI 2.0 でも同じ幅なので、ただの整数です。

### 適用の順序

- 同じ入力に複数のルートがあるときは**ルートの登録順**に処理する
- ルート間は独立。あるルートのフィルタや変換が他のルートへ影響しない
- 3 段はつねに入力前処理 → ルート → 出力後処理の順

この決定性のおかげで、パイプライン全体の挙動をホスト上のテストで固定できます。

## 駆動はキュー + 明示 `update()`

受信は各基盤ライブラリのコールバックで届きます。そのコールバックは USB Host タスクや NimBLE ホストタスクの文脈で走るので、そこから別の transport へ直接送信しません。

```text
ポートのコールバック(transport のタスク文脈)
        ↓  メッセージをキューへコピー
      キュー
        ↓  loop からの明示 update()
ルーティング → フィルタ → 変換 → 出力ポートへ送信
```

- MIDI 1.0 のメッセージは最大 3 バイトなので、キューのエントリは固定長で足り、コピーのコストは無視できる
- SysEx は**チャンクを一時バッファへコピーして積む**
- バッファやキューがあふれたら**捨ててカウントする**。カウンタは診断で読める([REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) の「入力が破棄されたか」)
- `update()` を呼ぶのはスケッチの `loop()`。core は自前のタスクを立てない([CORE_DESIGN.ja.md](CORE_DESIGN.ja.md))
- **`update()` が処理するのは、その呼び出し時点で積まれていた分だけ。** 段の中から注入されたメッセージは次の `update()` に回るので、アプリのフィードバックが 1 回の `update()` を無限に回すことがない

[DATA_MODEL.ja.md](DATA_MODEL.ja.md) の「ポインタはコールバック実行中だけ有効」という規約は、この構造で意味を持ちます。ポートから受け取った時点で core がキューへコピーするので、ポート側は転送先の都合を知らずにワイヤのバッファをそのまま渡せます。

## SysEx ストリームの規則

長い SysEx を認めた結果、3 つの規則が必要になります。

### 規則 1: 経路は開始時に確定する

`chunkStart` の時点で経路とフィルタの判定を決め、`chunkEnd` までその経路を維持します。途中でルーティング設定が変更されても、進行中のストリームは最初に決めた経路を守ります。

フィルタは `chunkStart` でのみ評価します。途中のチャンクで判定が変わると、SysEx が途中で切れた壊れたストリームが出力されます。

### 規則 2: 切断時はストリームを閉じる

入力ポートが切断されたら、進行中の SysEx は破棄します。ただし**すでに送り始めていた出力へは `0xF7` を送って閉じます**。受け手を待たせ続けないためです。

### 規則 3: 出力ポートの SysEx は排他

多対一の統合で複数の入力の SysEx が同じ出力へ同時に流れると、インターリーブして壊れます。出力ポートが SysEx を送信中は、別のストリームをその出力へは通しません(拒否してカウント)。送信元の他の宛先へは通常どおり流れます。

**System Real-Time(0xF8〜0xFF)だけは MIDI 仕様どおり割り込みを許します。** MIDI Clock が SysEx の転送中に止まらないためです。

**それ以外のメッセージは捨ててカウントします。** 当初は「待たせる」としていましたが、待たせるには出力ごとの遅延バッファが必要になり、容量管理と順序保証という別の問題を持ち込みます。MIDI のワイヤ上でも `0xF0` と `0xF7` の間に通常のメッセージは送れないので、**遅れて届くより落ちたと分かるほうが診断できます**。カウンタで可視化します。

この 3 規則は MIDI 2.0 でも変わりません。UMP でもデータメッセージのストリームは group ごとに同時 1 本という制約なので、そのまま地続きです。

## ループ防止

### 既定: 同一エンドポイントへは戻さない

あるエンドポイントの入力ポートから入ったメッセージは、**既定では同じエンドポイントの出力ポートへ送りません**。USB MIDI キーボードから来たノートをそのキーボードへ返すのは通常望まない挙動です。

[DATA_MODEL.ja.md](DATA_MODEL.ja.md) で入力ポートと出力ポートの所属エンドポイントが判別できるので、この規則は構造的に成立します。

意図的にエコーバックしたい構成のために、ルート単位で解除できるようにします。既定は禁止です。

### 多段の循環は内部では起きない

`A入力 → B出力` と `B入力 → A出力` を両方設定しても、**EspMidi の内部では循環しません**。ルーティングは In → Out の一方向で、内部に Out → In の辺が存在しないからです。A の演奏は B へ出てそこで終わり、B の入力ポートへは戻りません。

戻るとしたら機器 B がエコーバックした場合で、それは EspMidi から見えない外部配線です。したがって**ルート追加時の静的循環検査は持ちません**(検査対象が存在しないため)。

実在するのは次の 2 つで、どちらも上の既定規則が覆います。

- 同一エンドポイントへの送り返し
- アプリケーションポートの自己ループ(`app.in()` → `app.out()`。同じエンドポイントなので同じ規則で防がれる)

アプリが 2 つのアプリケーションポートを使って自分で環を作った場合は、キュー越しに 1 周ずつ進みます。`update()` が 1 回で処理するのは呼び出し時点の分だけなので、1 回の `update()` が回り続けることはありません。

## 無効なポートの扱い

- 切断中の入力ポートからはメッセージが来ない。ルートは残る
- 切断中の出力ポートへの送信は失敗を返す。ルートは残り、カウンタが増える
- 出力ポートが混雑している(キューが埋まっている)ことは診断で読める
- どのポートで問題が起きたかは、ポートのハンドルとメタデータで特定できる

ルートが無効なポートを指しているだけでエラーにはしません。機器の抜き差しは通常運用であり、例外ではないためです。

## アプリケーションポート

トランスポートに裏打ちされないポートです。スケッチがメッセージを注入し、受け取ります。**アプリケーションは特別扱いではなく、UART や USB ケーブルと並ぶポートの 1 つ**として扱われます。席も群もループ規則も同じです。

```cpp
espmidi::AppPort app(router, "monitor");

// 観測: パイプラインから届いたものを受け取る
app.onMessage(handler, this);
router.addRoute(usbHostIn, app.out());

// 注入: 作ったメッセージをパイプラインへ流す
router.addRoute(app.in(), uartOut);
app.sendShort(0xb0, 7, 64);
```

用途の使い分けは次のとおりです。

| したいこと | 使うもの |
| --- | --- |
| 見る / ログ / LED / ディスプレイ | アプリケーションポート(出力側) |
| 作る / 注入(ボタン、エンコーダ、MIDI Clock 生成) | アプリケーションポート(入力側) |
| 通す・落とす・書き換える(1 → 1) | 段のコールバック |
| 1 → N、別種のメッセージを出す | コールバックからアプリケーションポートへ `send()` |

Control Mapping ヘルパー([REQUIREMENTS.ja.md](REQUIREMENTS.ja.md))はこの上に乗ります。

**`send()` は即時再帰しません。** 注入されたメッセージはキューに積まれ、次の `update()` で処理されます。段の中やコールバックの中から呼んでも、いま走っているパイプラインに割り込みません。

## チャンクの扱い

**チャンクが通るのはフィルタだけで、しかも最初のチャンクだけです。** 規則 1 が「経路は開始時に確定する」と定めている以上、途中で判定を変えることはあってはなりません。変換とコールバックはチャンクを一切見ません — データストリームの中身を解釈するのは EspMidi の役目ではないからです。SysEx を加工したい場合はアプリケーションポートで受けて自前で処理します。

フィルタが最初のチャンクを弾いた場合、その出力は**ストリームを掴みません**。掴んでしまうと、送っていないストリームで出力が塞がったままになります。

**チャンクはキューの容量に応じて分割されます。** 1 エントリが運べるペイロードは `ESPMIDI_CHUNK_BYTES`(既定 48)なので、これを超えるチャンクは複数エントリに分かれます。**`chunkStart` は最初の断片だけ、`chunkEnd` は最後の断片だけ**が持つので、下流から見れば 1 本のストリームのままです。チャンクの境界そのものは意味を持たないため、この分割は安全です(結合はしません)。

## 診断カウンタ

配送されなかったメッセージは必ずどこかで数えられます([REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) の可視性)。

| カウンタ | 意味 |
| --- | --- |
| `received` | ポートから受け取った数 |
| `queueFull` | キューが満杯で捨てた |
| `delivered` | 送信に成功した |
| `sendFailed` | ポートが送信を拒否した(切断中など) |
| `droppedByFilter` | 宣言的なフィルタが弾いた |
| `droppedByStage` | 変換が表現できなかった、またはコールバックが `Drop` を返した |
| `sysExRejected` | 送信中の出力へ 2 本目のストリームが来た(規則 3) |
| `blockedBySysEx` | ストリーム送信中で送れなかった(規則 3) |
| `noRoute` | 宛先が 1 つも無かった |
