# 設定モデル

`EspMidi` の設定の考え方と、保存先や設定 UI を core の外に置く理由のメモです。

## 設定は実行時のオブジェクト

ルート、フィルタ、変換、ポート群はすべて実行時の API で組み立てます。設定ファイル形式や設定用の DSL を core に持ちません。

```cpp
espmidi::Route r = midi.addRoute(inPort, outPort);
// フィルタと変換はルートに対して設定する(具体的な形は Phase 4 で確定)
```

理由は 2 つです。

1. **設定は動作中に変更できることが要件**([REQUIREMENTS.ja.md](REQUIREMENTS.ja.md))。ファイルを読んで起動時に固める形だと、機器の抜き差しやモードの切り替えに追従できません。
2. **ポートの席は動的に増減する。** 静的な設定記述だけでは、実行中に現れたポートを指せません。

## 保存先を core に持たない

設定の永続化(NVS、SPIFFS、LittleFS、SD、外部 EEPROM)は core の責務外です。

- 保存先の選択はアプリケーションの事情で決まる
- 保存形式(JSON、CBOR、独自バイナリ)も同様
- core が保存先を持つと、保存を使わない構成でも依存が増える

`EspMidi` は「設定オブジェクトを組み立てて適用する API」を提供し、その設定をどこから読んでどこへ書くかはスケッチが決めます。ESP32KeyBridge と同じ方針です。

## 設定 UI を core に持たない

WebSerial、CDC、Web サーバ、ディスプレイなどの設定 UI も core の外です。実装するとしても reference example の側に置きます。

## 既定値の方針

設定しなくても素直に動くことを重視します。

- **ループ防止は既定 ON**(同一エンドポイントへは戻さない)。危険側が既定にならないようにする
- **フィルタと変換は既定なし**(素通し)
- ルートを 1 本も作らなければ何も転送されない。暗黙の「全入力 → 全出力」は作らない

暗黙の全結合を作らない理由は、それが望ましくない構成(自分の入力が自分の出力へ返る、意図しない機器へ演奏が流れる)を既定にしてしまうためです。

## 診断情報の読み出し

設定と同じく、診断も実行時 API で読みます([REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) の可視性)。

- ポートの状態(利用可能 / 切断中 / 未接続)
- 破棄したメッセージ数
- 送信失敗の数
- 出力の混雑

ログ出力の形式や出力先は core が決めません。スケッチが読んで好きな形で出します。

## 未確定事項

設定オブジェクトの具体的な形(3 段パイプラインそれぞれの設定の書き方、値の幅を後から広げられる API 形状)は Phase 4 の実装時に確定します([DECISIONS.ja.md](DECISIONS.ja.md) の仮置き 1)。
